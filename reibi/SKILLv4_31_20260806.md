>

### 錯誤R：str_replace anchor 行在替換後消失
**現象**：`str_replace` 的 `old_str` 以某函數宣告行（如 `var hashPin=async function(p){`）結尾，但 `new_str` 沒有把這一行帶進去，導致該行永久消失，後續出現 `SyntaxError: Unexpected reserved word`。

**解法**：
1. 插入前心算：`new_str` 的最後一行，是否需要把 `old_str` 的某些字再帶一遍？
2. 最保險寫法：anchor 行同時放入 `old_str` 末尾 **和** `new_str` 末尾（確保替換後仍存在）
3. 每次 `str_replace` 後馬上跑 `node --check`

> ⚠️ **延伸案例（2026-07-07新增）**：本次在兩個既有函數之間插入一整個新函數（`PartnersScreen`）時，`new_str`只寫到新函數的結尾`}`，忘記把緊接在插入點後方的「下一個既有函數宣告行」（`function ApptMgmtScreen(props){`）帶回去，導致該行連同其上方的兩行註解一起消失，`ApptMgmtScreen`的函數體變成孤兒程式碼，觸發`Illegal return statement`。**跟原本的錯誤R是同一個根本原因（anchor行沒有同時出現在old_str和new_str），但這次的「anchor行」是被插入點截斷的下一個函數宣告，不是被修改函數自己的宣告行，容易漏想到。規則更新：在兩個既有函數之間插入新函數時，`old_str`與`new_str`都必須完整包含「插入點之後緊鄰的下一個函數宣告行」（含其上方的區塊註解），不能只寫到新函數結尾就收手。**

### 錯誤X：大型程式碼插入的括號平衡計算錯誤（2026-07-05 新增）⭐

**現象**：本 chat 中插入 OHSPlanScreen（約 400 行）和 ROI SVG 折線圖（約 80 行）後，主平台 `node --check` 報 `SyntaxError: Unexpected token ')'`，錯誤行顯示在 ParamsScreen 的最後一行（`null)));`），但實際問題在距離出錯行 100+ 行之前插入的 SVG chart 區塊。

**根本原因（三個層次）**：

1. **SVG 折線圖插入後，results Card 的關閉括號位置改變**：原本 IBox 是 results Card 最後一個子元件，IBox 那行的第三個 `)` 同時關閉了 results Card。我把 IBox 的 `]))` 改為 `]))`（少一個 `)`，讓 results Card 保持開啟），然後在後面加入 chart div 作為 Card 的新子元件，chart div 的 `))` 再關閉 chart + Card。邏輯正確，但實際 Python 替換時 `OLD_ROI_CARDS` anchor 的結尾計算出現偏差，導致 results Card 多了一個 `)` 或少了一個 `)`。

2. **括號計算工具對「跨行 ce() 巢狀結構」計算不準確**：我使用的括號稽核工具計算函數邊界的 `(` vs `)` 差值，但對於複雜巢狀的 `ce()` 樹，「這個 `)` 到底是關閉哪一層」需要追蹤巢狀深度，單純計數差值無法反映結構正確性。

3. **Python 的大型多行字串在 f-string 和 repr 切換時的特殊字元問題**：patch 腳本中部分 anchor 字串因含有 Unicode escape（`\u842c` 等），在 Python 字串比對時會被誤處理。

**正確解法（本次實際採用）**：

```
步驟一：插入後立即用括號稽核工具確認修改函數的 diff=0
步驟二：若 diff≠0，用「逐行追蹤 paren balance」工具找出哪行讓餘額變負
步驟三：不要猜測，要用精確計數確認每個 ce() 結構的開閉
步驟四：最後一行 null))) 這類 Screen 關閉行，如果插入了新的子元件，
        先數清楚 Screen 現在有幾個頂層子元件，關閉符號數量是否對應
步驟五：調整最後一行的 ))) 數量（+1 或 -1），直到整個函數 diff=0 且 node --check 通過
```

**逐行追蹤 paren balance 工具**（v4.15新增，2026-07-07驗證仍為最實用做法）：
```python
depth=0; in_str=False; str_ch=None
for i,line in enumerate(lines[start:end],start=start+1):
    for ch in line:
        if not in_str:
            if ch=='"' or ch=="'": in_str=True; str_ch=ch
            elif ch=='(': depth+=1
            elif ch==')': depth-=1
        else:
            if ch=='\\': continue
            elif ch==str_ch: in_str=False
    print(i,depth,line.rstrip()[-55:])
# 比對插入點前後、同一巢狀層級的兄弟節點，depth是否一致
```

> ⚠️ **2026-07-07再次驗證有效**：在l5.jsx的`DistributorScreen`裡插入「PIN管理面板」這一大塊UI(約20行、3層巢狀ce())時，第一次插入後`node --check`通過，但實際上是插入點前一個Card沒有正確關閉，導致新插入的Card變成該Card的子節點而非兄弟節點——這種「語法上合法但語意上巢狀關係錯誤」的情況，`node --check`不會報錯，必須用上述逐行追蹤工具比對「插入前這個位置的depth」跟「插入後同一位置理論上該有的depth」是否一致才能抓到。**規則：插入超過3層巢狀的大塊UI，即使`node --check`通過，仍建議額外跑一次逐行深度追蹤，比對插入點前後的depth走勢圖，確認新插入的區塊是在正確的巢狀層級上。**

**預防原則（插入大型 UI 區塊時）**：
1. 每次插入超過 20 行的新 `ce()` 區塊後，立即跑括號稽核
2. 若新 ce() 區塊是某個 Card 的「最後一個子元件」的替換，特別注意：原先那個子元件的最後一行是否也承擔了關閉更外層容器的責任（如 Card、slider 外層 div）
3. 複雜插入（修改原有 ce() 結構）優先使用「先確認現有括號結構、再插入、再驗證」三步驟，而非直接替換

### 錯誤Y：useState宣告與實際使用不同步（2026-07-07新增）⭐

**現象**：`NewCaseScreen`裡`setHandoffApplied(true)`跟`handoffApplied&&ce(IBox,...)`都存在，但整個檔案搜尋不到`var[handoffApplied,setHandoffApplied]=useState(...)`這行宣告——這個state從一開始就沒有被正確宣告過，是使用者上傳檔案裡本來就有的既有缺陷。使用者實際在Claude.ai介面打開這個artifact測試時，畫面直接顯示錯誤對話框：「運行工件時出錯：handoffApplied 未定義」。

**根本原因**：這種bug用眼睛看程式碼很難發現，因為`setHandoffApplied`跟`handoffApplied`兩個識別字本身「看起來」很正常、很像有被宣告過，只有真正執行渲染到那一行才會炸開（且因為是`&&`短路寫法，只有畫面切到那個特定分頁才會觸發，容易在只做過部分畫面測試的情況下漏掉）。

**檢測方法**：寫一段regex腳本比對「所有`setXxx(`呼叫」跟「所有`[xxx,setXxx]=useState`宣告」，找出呼叫了但沒宣告的setter：
```python
import re
declared=set(re.findall(r'\[\s*\w+\s*,\s*(set\w+)\s*\]\s*=\s*useState', c))
called=set(re.findall(r'\b(set[A-Z]\w*)\s*\(', c))
missing=[m for m in sorted(called-declared) if m not in ("setFullYear","setMonth","setTimeout")]
```
注意排除`setFullYear`/`setMonth`/`setTimeout`等JS內建方法造成的假陽性，以及`props.setXxx&&props.setXxx(...)`這種guarded的可選prop呼叫（這是合法的可選props模式，不是bug）。

**建議時機**：每次大改動後、或收到使用者回報「運行時出錯」但錯誤訊息只是一個變數名時，第一步就跑這個腳本，比逐行閱讀程式碼找漏宣告快得多。

### 錯誤Z：emoji使用ZWJ(Zero Width Joiner)組字元（2026-07-07新增）

icon:"🧑‍💼"  // ❌ 這是"🧑"+ZWJ(U+200D)+"💼"組成的複合emoji

### 錯誤AH：`parseInt("")||0`把「空白/未輸入」誤判成「數值0」，0又被業務邏輯誤判成落入最小級距（2026-07-08新增，quote v1.9修正）⭐⭐⭐

(1) `calcAFee`函式對人數欄位做`var n=parseInt(memberCount)||0`，當`memberCount`是空字串(使用者根本還沒選/沒填)，`parseInt("")`回傳`NaN`，`NaN||0`得到`0`，接著業務邏輯`if(n<=tier.max)`第一階「≤100人」的判斷`0<=100`為true，於是「尚未輸入」被誤判成「≤100人的基本型客戶」，算出NT$57.0萬(60萬基本費×5%年繳折扣)。

```js
// ❌ 空白被parseInt||0吃成0，0又被<=判斷誤收進最小級距
function calcAFee(memberCount,payMode){
  var n=parseInt(memberCount)||0;
  var base=0;
  for(...){if(n<=tier.max){base=tier.annual;break;}}  // n=0時第一階(0<=100)就命中
  ...
}

// ✅ 修正：先判斷「是否為空白/未輸入」，是的話直接回傳0，不進入任何級距判斷
function calcAFee(memberCount,payMode){
  if(memberCount===""||memberCount===null||memberCount===undefined)return{base:0,final:0,note:"尚未輸入人數"};
  var n=parseInt(memberCount)||0;
  ...
}
```
**教訓**：`parseInt(x)||0`這個常見寫法把「轉換失敗(NaN)」和「合法輸入0」都變成同一個值`0`，如果下游邏輯對「0」有實際業務意義（例如這裡的「0人也會落入最小人數級距」），就會把「使用者根本還沒填」誤判成「使用者填了一個會產生實際金額的合法值」。凡是有「級距/門檻」判斷的欄位，開發時要先問「空白/未輸入的狀態，應該對應到哪個結果？」，通常答案是「不套用任何級距，回傳0或明確的『尚未輸入』狀態」，不能讓它意外落進第一個級距區間。同時，UI上任何「快選數字」若對應到後端有明確定義的級距/門檻表，應該直接從權威定義(`PRICING.A.tiers`)取值產生，不要另外手打一組示意數字，避免兩邊對不上。

**判定**：這不是程式碼寫錯，而是**Claude.ai已發布artifact的沙盒環境安全性限制**，會攔截`blob:`URL的下載/導覽行為。與本專案先前發現的「四系統storage互相隔離」屬於**同一類別**——都是Claude.ai artifacts平台本身的架構限制，程式碼邏輯完全正確也無法繞過，只能換一種不觸發同一機制的做法。
**修正**：改用「顯示文字內容+複製到剪貼簿」取代下載動作。新增一個可展開的唯讀`<textarea>`顯示範本內容，搭配`navigator.clipboard.writeText()`複製按鈕(失敗時退回提示使用者手動全選`Ctrl+A`+複製`Ctrl+C`)。純文字複製不涉及`blob:`URL導覽/下載機制，在沙盒環境下可正常運作。
**類比判斷原則**：`window.print()`(叫出瀏覽器原生列印對話框)屬於**不同機制**，不受此限制影響——本專案`OHSPlanScreen`/`DeptMgmtScreen`的列印功能都用`window.print()`，事後確認未受影響，仍正常可用。
**教訓**：這類「瀏覽器API語法正確、但在特定沙盒/iframe環境下被安全性政策封鎖」的問題，`node --check`、括號稽核、甚至`react-dom/server`渲染測試都測不出來，因為這些工具測的是**程式碼結構**，不是**瀏覽器沙盒執行環境的權限限制**。日後任何要用到「觸發瀏覽器原生行為」的功能(檔案下載、開新視窗、剪貼簿、地理位置、通知權限等)，交付前應該提醒使用者**務必在已發布的artifact上實測**，不能只靠程式碼審查判斷會不會動——語法正確不代表沙盒環境會放行。遇到類似「這項內容已遭到封鎖」「Permission denied」這類瀏覽器安全性錯誤頁時，優先懷疑是沙盒環境限制，而非先假設自己程式碼寫錯，並在SKILL.md/PROJECT_INSTRUCTIONS.md建立清單，記錄哪些瀏覽器API在這個環境下能用、哪些不能用，避免同樣的坑重複踩。

with open('檔名.jsx','r',encoding='utf-8') as f: c=f.read()
c=c.replace('\uFE0F','').replace('\uff08','(').replace('\uff09',')')
vs=sum(1 for ch in c if ord(ch)==0xFE0F)
zwj=sum(1 for ch in c if ord(ch)==0x200D)
jsx=c.count('return<')
fixed='position:"fixed"' in c or 'position:"sticky"' in c
wide=sum(1 for ch in c if ord(ch) in(0xff08,0xff09))
in_str=False;real_nl=0
for ch in c:
    if not in_str:
        if ch=='"':in_str=True
    else:
        if ch=='\\':continue
        elif ch=='"':in_str=False
        elif ch=='\n':real_nl+=1
lines=c.count('\n')+1;size=len(c.encode('utf-8'))
print(f"VS:{vs} ZWJ:{zwj} JSX:{jsx} fixed:{fixed} Wide:{wide} RealNL:{real_nl}")
print(f"Lines:{lines} Size:{size//1024}K")
# 全部目標：VS=0 ZWJ=0 JSX=0 fixed=False Wide=0 RealNL=0
with open('檔名.jsx','w',encoding='utf-8') as f: f.write(c)

本次的`partners`/`staff`畫面「開發中」佔位bug，本質上跟第五十九節記錄的經銷商登入bug是同一類型教訓（程式碼寫了、UI路由沒接上），但呈現方式不同：不是完全沒有渲染路徑，而是**正確路徑跟兜底佔位路徑同時滿足渲染條件**，兩者一起被畫出來，使用者只看到佔位卡在最上面就以為整頁沒做。**教訓：「開發中」這類兜底佔位UI，如果是用排除清單（而非明確畫面清單）控制顯示時機，每次新增畫面都要交叉檢查這份清單，且这種bug無法從程式碼「看起來合理」判斷出來，必須實際導覽到該畫面才能發現。**

### 26. 金額欄位bug的教訓：使用者截圖裡「輸入的值」與「顯示的結果」同時存在，是抓單位換算bug最快的方式
使用者截圖同時顯示了輸入框內容（"171"、"7"）跟下方计算結果（"NT$0.0萬/年"），這種「輸入值+輸出值同框」的截圖，比純文字描述「金額不對」更容易讓人一眼定位問題屬於單位換算而非公式邏輯錯誤（如果是公式錯，通常不會剛好差1萬倍）。**教訓：請使用者回報金額類bug時，若能同時看到「使用者填了什麼」與「系統顯示什麼」，優先檢查兩者之間是否有單位換算的落差（萬/元、%/小數等常見陷阱），這類bug比邏輯錯誤更常見也更快修。**

### 27. 新增「選填、可稍後補登」欄位時，要主動規劃「稍後在哪裡補登」的完整路徑，不能只做建立時的輸入框
使用者要求D層場域地點「報價階段先不列入，後續業務/客服依實際場勘內容補登」。單純在quote.jsx報價表單加一個選填欄位並不夠，因為quote.jsx建立後的資料流是quote→合約→handoff→l5正式建檔，「稍後補登」必須同時確保：(1)quote端能編輯、(2)合約轉換與handoff都要把這個欄位帶過去不遺漏、(3)l5端正式建檔後（`EnterpriseScreen`）也要能持續編輯更新，不能只有建立當下的`NewCaseScreen`能填。**教訓：「選填、可稍後補登」的欄位，要主動畫出資料從產生到最終落地的完整路徑圖，在每一個中繼站（表單→儲存→轉換→交接→正式記錄→事後編輯）都要確認這個欄位有被帶著走，任何一站漏接都會讓「稍後補登」變成事實上補不到。**

### 28. 主動检查「新資料要不要順便通知/串接第三個相關檔案」，即使使用者沒有明確要求
在完成quote.jsx↔l5.jsx的D層場域資料串接後，主動檢查`doHandoffWorkOrder`（給reibi-workorder.jsx的交接payload）是否也該帶上這個新欄位——結果發現真的漏了。但因為`reibi-workorder.jsx`當次對話沒有被上傳，沒有檔案內容就不能修改它本身，只能先把payload補上讓資料到位，等下次拿到檔案再處理顯示邏輯。**教訓：改動涉及多檔案共用的資料模型時，主動比對「還有哪些檔案的交接/串接邏輯理論上也需要這個新欄位」，即使使用者當次沒提到；但同時要遵守「沒看過的檔案不能憑印象修改」的原則，只能做「自己這邊先把資料準備好」的部分，並明確告知使用者另一邊還需要後續處理。**

### 29. 「這個欄位好像沒有」不能只看使用者截圖判斷，要grep確認是「真的沒有」還是「有但沒被用到」
使用者上傳`reibi-workorder.jsx`後，開工前grep發現`WorkOrderForm`裡其實**已經有**`address`欄位（標示「施工地址 *」，還是必填），但handoff自動帶入的`useEffect`裡漏了讀取這個欄位這一行，導致每次從quote.jsx交接過來都要業務自己重打一次地址。如果沒有先grep就直接「新增address欄位」，會做出重複的第二個地址欄位，或覆蓋掉原本運作正常的手動輸入邏輯。**教訓：「這個功能好像沒接」的假設，永遠要先grep確認是「完全不存在」還是「存在但某個環節(通常是handoff/prefill這類串接膠水程式碼)沒接上」，兩者的修法完全不同——前者要新增欄位，後者只要補一行讀取邏輯。**

### 30. 使用者自己提出的新角色/新流程設計，回答前先確認該角色在系統既有架構裡的真實定位
使用者一開始構想workorder的交付範圍確認要「雙方甚至三方」，並猜測第三方可能是經銷商。在回答前先查證了經銷商在整個系統裡的角色定位——第六節/五十九節的經銷商設計從頭到尾只圍繞`calcDistComm`分潤計算，是銷售通路角色，從未涉及D層實體施工執行。把這個發現回饋給使用者後，使用者自己確認這個第三方確實是角色混淆，主動簡化為REIBI+客戶兩方。**教訓：使用者自己提出的新設計如果牽涉「新增某個既有角色到新流程裡」，在直接照做之前，先花一分鐘查證這個角色在系統裡目前的真實職能範圍，把查證結果攤開給使用者看，比直接照字面實作、事後才發現角色錯位要更有效率——很多時候使用者自己也還在構思階段，看到具體的既有架構描述反而能幫助釐清真正的需求。**

## 本次 Session（2026-07-08）—— storage不共用重大發現，三系統bug盤點

### 31. 「未定論」拖了三個版本才真正被驗證，教訓是：關鍵技術假設要盡早逼自己去實測，不要一直停留在「待確認」
從v4.15的「已確認隔離」，到v4.16~v4.18改成「未定論」，中間橫跨好幾輪session，這個問題一直用文字警示提醒「需要使用者實測」，但實際上一直沒有真正發生，直到2026-07-08使用者自己發布四個artifact並交叉測試才真正水落石出。回頭看，這中間quote.jsx/l5.jsx/workorder.jsx新增的好幾個「跨artifact讀取」功能（接單來源選擇器讀l5_staff、workorder讀quote合約清單等），都是在「未定論」狀態下繼續往上疊加開發的。**教訓：發現一個會影響架構方向的關鍵技術假設處於「未定論」狀態時，應該優先建議使用者盡快驗證，而不是在假設成立的前提下繼續疊加新功能——疊得越多，一旦假設被推翻，需要重新盤點「哪些功能其實一直沒真正生效」的範圍就越大。**

### 32. 「看起來正常運作」不等於「真的如預期運作」——storage未Publish時的靜默失敗，製造了假的驗證通過
先前誤判「l5能讀到quote的rq_quotes統計」，事後回顧才發現當時artifact根本沒Publish，storage呼叫本來就會靜默失敗、回傳空值，剛好與「還沒有資料」的正常狀態長得一模一樣，才會被誤判成「共用成功」。**教訓：任何依賴不會拋出明確錯誤訊息的API（存檔靜默失敗、讀取回傳預設值），驗證時要主動製造「有意義的差異」（例如先寫入一個獨特的測試字串，讀取端如果讀到才算過），不能只看「有沒有報錯」或「畫面有沒有顯示東西」，因為兩種失敗模式(真的沒資料 vs API根本沒執行)在UI上可能長得一樣。**

### 33. 大方向決策（不合併/不接後端）確定後，之前「留了容錯機制」的程式碼就是最好的安全網，不用砍掉重寫
本次發現storage不共用後，原本可能需要把整個session辛苦做的handoff/跨讀功能全部砍掉重做，但因為當初每一個跨讀功能都遵循「讀不到就退回手動輸入」的設計原則（例如`l5Staff&&l5Staff.length>0?下拉選單:文字輸入`），現在只是那個容錯分支變成永遠會走的路徑，系統本身完全不受影響，只是拿不到「自動預填」的加分效果。**教訓：設計任何依賴外部/不確定資料來源的功能時，容錯分支不是防禦性寫作的形式主義，而是真正的風險對沖——當外部依賴後來被證實整個不可靠時，容錯分支能讓系統直接優雅降級，不需要回頭重寫。**

## 本次 Session（quote v1.8～v1.11，2026-07-08）—— 經銷商報價單存讀bug、QuickQuote計算bug、正式列印格式

### 34. 「圖片截圖回報bug」比純文字描述更容易讓AI快速定位根因，但仍需自己grep驗證，不能只憑畫面推測
使用者這次多次用手機截圖回報問題（QuickQuote畫面顯示570000、171萬；經銷商報價單編輯後空白），比起純文字「報價單有問題」更快讓人聚焦到具體是哪個畫面、哪個數字。但截圖只能告訴你「症狀」，實際根因（`calcAFee`對空白值的處理、`doSave`欄位對應邏輯）仍然要靠grep程式碼並追蹤資料流向才能定位，不能單憑畫面猜測就直接下修正——本次「A層570000」跟「編輯後空白」表面上像同一個bug，實際上是完全不同函式(`calcAFee` vs `doSave`欄位對應)的兩個獨立根因，只是恰好都跟isDist/空白輸入有關。

### 35. 使用者報的「問題」有時候是對UI設計的期待，不一定是程式錯誤——先問清楚要修的是「行為」還是「顯示方式」
「A層軟體年授權費為60萬」這句回報，一開始容易誤判成「金額算錯了」，但實際查證後發現金額本身沒算錯(57萬=60萬基本費×95%年繳折扣，兩個數字都對)，使用者要的其實是「模板價」這個標籤該對應到哪個數字的定義問題——是要顯示折扣前的官方定價(60萬)，還是折扣後的實際金額(57萬)？這類回報如果不先分辨「數字算錯」vs「數字對但標籤/呈現方式不是使用者預期的」，容易做錯修正方向(去改calcAFee的計算邏輯，而不是去改顯示邏輯)。**教訓：收到「數字不對」類回報時，先用計算機或程式邏輯獨立驗證一次「這個數字本身是否正確」，如果驗證後數字沒錯，那問題多半出在標籤/呈現方式，而不是計算邏輯本身。**

### 36. 長表單/長頁面的錯誤提示，要考慮使用者當下實際的捲動位置，不能只放在固定的一個地方
「確認試算按鈕無反應」查證後發現按鈕邏輯完全正確，只是驗證失敗的Toast固定顯示在頁面最上方，而使用者操作到按鈕時通常已經捲到頁面底部。這類bug的特徵是「單獨測試時可能發現不了」——如果開發時測試都是從頭捲動看著整個頁面操作，會看到Toast正常跳出；但真實使用情境是使用者只盯著自己正在填的區塊/按鈕，很可能完全錯過遠處的提示。**教訓：任何互動元件的回饋（成功/失敗提示），設計時要以「使用者當下視野範圍」為準，不能假設使用者會看到頁面上任何位置出現的訊息，尤其在可捲動的長頁面上。**

### 37. 新增「列印/PDF」類功能時，要連帶檢查共用元件是否真的支援你要用的prop，不能只看呼叫端語法正不正確

### 41. 新增「跨畫面共用資料」的功能（如下拉選單需要讀取另一個畫面管理的清單）前，先確認目前畫面有沒有載入這份資料的state/useEffect

## 本次 Session（quote v1.12、l5 v2.13，2026-07-14）—— docNo流水號化、角色權限文字核對、對應服務人員欄位

### 42. 跨檔案複製一個「已驗證過的模式」時，先看清楚原始實作的資料格式差異，不能整段照抄

### 43. 「查證後發現不需要改」本身也是一個有效的處理結果，不用為了交差硬找東西改
「quote.jsx/workorder.jsx的3-7工作日文字是否需要同步」這個待辦，查證後發現：quote.jsx確實有4處舊文字需要同步修正；workorder.jsx完整grep後發現**根本沒有**「現場勘查」相關文字（因為workorder.jsx處理的是勘查完成、正式報價確定後的施工執行階段，跟報價試算階段的現場勘查敘述本來就不該出現在同一份文件）。這種情況下正確的處理方式是明確回報「已確認不需要改」並附上grep依據，而不是因為待辦事項要求「同步」就勉強在workorder.jsx裡加一句用不到的文字。**教訓：待辦事項的措辭(例如「同步」)不代表結論一定是「要改」，grep驗證後如果發現目標檔案根本不適用，如實回報「查證後不適用」跟回報「已修正」同樣是有效的工作產出，不要為了讓每個待辦都有修改記錄而畫蛇添足。**

### 44. 「畫面上給人看的說明」跟「程式碼實際的權限判斷」是兩份獨立維護的資料，例行核對時要用結構化方式逐一比對，不能憑印象掃過去

### 60. 使用者截圖裡「看起來卡住」的錯誤訊息，未必代表現在真的卡住——要先確認畫面上其他欄位的存在，反推狀態機當下實際所在的分支
使用者截圖顯示「請先選擇使用方式」紅字錯誤同時跟「單位代碼/角色/管理者PIN」欄位一起出現，乍看矛盾(因為程式邏輯上，這些欄位只有在mode已經選定後才會渲染，理論上不該同時出現這個「尚未選擇」的錯誤)。查證`setErr("")`的呼叫時機(在`doLogin`一開始就會清空)，判斷這是「上一次按登入時觸發的錯誤，尚未被下一次點擊清除」的**殘留UI狀態**，不是當下真的卡住。**教訓**：畫面上的錯誤/提示文字不一定代表「現在」的狀態，有可能是「上一次操作」留下的殘影，只在下次觸發對應動作時才會更新或清除。排查這類疑似矛盾的截圖時，先找出「這個文字被設定/清除的所有時機點」，反推目前顯示的內容是「即時反映」還是「尚未更新的舊值」，比直接照字面斷定系統卡住更準確。

### 61. 新增依賴脈絡(如上層選單)動態呈現內容的功能，直接用既有state變數反應式(reactive)重新計算，不需要額外同步邏輯
新增部門L3/L4建議清單時，選單內容需要依照使用者選的「上層部門」動態切換。因為React元件每次重新渲染都會重新執行函式本體，`contextPresets`/`presetLabel`只要用一般變數(非state)在渲染時依當下`newParent`/`depts`重新計算即可，不需要額外`useEffect`監聽`newParent`變化再手動`setState`同步——這樣還能避免「使用者切換上層部門後，已展開的建議清單內容沒有跟著更新」這種因為忘記同步而產生的新bug。**教訓**：只要目標值可以直接從現有state(props/state)透過簡單運算得出，優先用「渲染時計算的一般變數」而非「額外一份state+useEffect同步」，計算越簡單的衍生資料，越不需要獨立的state來鏡射它，可以減少一整類「兩份資料忘記同步」的bug可能性。

### 內容設計備查：L3/L4部門建議清單的設計原則
`L3_SUGGESTIONS`依`PRESET_DEPTS`既有30個L2部門名稱，各自配置2-4個常見組/課建議(例如「人力資源部」→薪酬福利組/招募甄選組/教育訓練組/員工關係組)，涵蓋人資、資訊、財務、業務、生產、法務、行銷等常見企業部門類型。因為L4(班/小組)命名慣例分歧很大(依產業/輪班制度差異太多，難以像L3一樣做出有意義的專屬對照)，改用一組通用建議(第一組/第二組/第三組/早班/中班/晚班/A組/B組)取代逐一對應。自訂命名、不在30項清單裡的L2部門，L3建議退回通用清單(規劃組/執行組/管理組/支援組)，確保任何情境下都有合理的建議可用，不會因為找不到對應資料而顯示空清單。

### 63. 舊版業務文件（合約/手冊/簡報）不能只當「排版範本」沿用，要先查證其中的事實性內容是否仍與系統現況相符
使用者提供舊版v4.3合約/手冊要求「更新」，若只是套用舊版的結構跟語氣，內容可能會沿用早已過時的規格數字（例如舊手冊聲稱「AI報告5,000字」，實際系統現況是「至少2,000-2,500字」；舊手冊聲稱雙層驗證是「群組碼+個人名稱清單選擇+PIN」，實際上「名稱」只是自由輸入的稽核代稱）。**教訓**：處理「更新舊版文件」類的任務時，要把它當成「重新核實所有事實性主張」的機會，而不是單純的排版/新增章節工作——舊文件裡的每一個具體數字、機制描述，都要重新grep程式碼驗證，抓到不一致要明確標註「本次核實發現」，而不是照抄舊版文字直接沿用。合約類文件尤其不能望文生義，任何找不到對應原始碼佐證的條款內容都不應該自己編造，要明確跟使用者說明資料來源受限、需要對方提供或確認。

### 64. 純視覺設計任務(簡報)的QA重點跟程式碼任務不同——要對照設計規範清單逐項自我檢查，而非只看「有沒有跑起來」
